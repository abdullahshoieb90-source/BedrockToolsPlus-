# Spatial GUI: initial groundwork

The goal is a chest interface displayed on a world-space panel, similar to the reference video. This is **not yet a usable in-game feature**. The first step is the engine-independent panel geometry in `src/modules/spatialgui/panel_geometry.hpp`, with host tests in `tests/spatialgui_panel_test.cpp`. An opt-in `Spatial GUI Diagnostics` module is registered; it only observes rendering and does not change the vanilla container screen. Spatial GUI itself is not registered or usable.

The geometry creates a vertical panel facing the viewer at creation time, returns its corners in top-left clockwise order, and maps a front-facing world ray to normalized top-left-origin coordinates. `input_mapping.hpp` unprojects a touch with a supplied OpenGL inverse view-projection matrix, then maps the hit to logical UI coordinates. The returned right/bottom edges equal the logical width/height, so an adapter using integer pixel indices must choose an appropriate edge policy. The unprojection assumes OpenGL clip-space depth [-1, 1]; this convention must be verified against the actual Minecraft rendering backend before integration.

A future integration should capture the panel pose once on opening, not recreate it every frame. It must supply the actual camera inverse view-projection and viewport from the same frame as the touch and account for viewport offsets, UI scaling and device orientation. The repository does not currently expose a verified inverse camera projection or a container screen render-to-texture API; the mapping helpers are not connected to game input.

## Touch event groundwork

The runtime publishes `TouchInputEvent` for every action delivered by Preloader, including pointer IDs, move and cancel. Events carry Android view coordinates, not GUI coordinates. Existing modules still receive exactly the same primary down/up/cancel callbacks unless a raw event subscriber explicitly consumes the event; no Spatial GUI subscriber is active yet. The launcher can send one MOVE or CANCEL callback per pointer. `touch_router.hpp` maps and tracks a single pointer, cancels when it leaves the panel, and returns a cancellation on close; its host tests do not deliver input to Bedrock. The inspected launcher consumes the entire Android MotionEvent if any pointer callback consumes a MOVE/CANCEL, so the router's per-pointer consume result cannot safely be used as-is when multiple fingers are active. `gesture_capture.hpp` models an exclusive alternative: it captures only on the initial DOWN and consumes every pointer until the complete Android gesture ends, while forwarding only the primary finger to the UI. It also keeps ownership after UI close until release. This policy has host tests but is not connected to the launcher or verified on a device; lifecycle interruptions and the launcher's per-pointer CANCEL behavior must be validated in practice. Do not consume anything until container rendering and input forwarding are operational.

## Android touch injection groundwork

`android_touch.cpp` implements an experimental single-pointer JNI adapter using the inspected launcher's `MinecraftActivityState.getCurrentActivity()` and `MinecraftActivity.dispatchTouchEventToGame(MotionEvent)` route. It only dispatches on the Android UI thread while the activity is resumed, creates a touchscreen event with a consistent down time, and avoids re-entering the Preloader callback by using the launcher's direct game dispatch method. Coordinates must be supplied in game-view physical pixels, not panel UV or logical UI units. Its JNI protocol has host fake tests, but has not been built or tested against Android, verified with the user's launcher version, or connected to spatial UI. The adapter reports only whether the Java call completed, not whether Bedrock accepted or handled the gesture. Input must remain unconsumed until the screen capture, coordinate transform, dispatch and lifecycle can be validated end-to-end.

## Off-screen target groundwork

`screen_capture.hpp` adds a single-call capture operation that clears to transparent and publishes a texture only after a successful frame, restoring framebuffer, viewport and clear state; it rejects framebuffer rebinds and recursive use. The callback is not yet tied to a Minecraft screen. `offscreen_target.hpp` provides an OpenGL ES 3 framebuffer with an RGBA texture and depth attachment, transactional resizing, scoped framebuffer/viewport binding, explicit render-thread cleanup and context-loss handling. It is not yet invoked by the game. Tests use a fake GL implementation; a real Android GPU and Minecraft's render-state tracking have not been tested. In particular, simply binding a GL framebuffer around a Bedrock UI call may not work if the engine tracks or changes its render target. Integration must restore both engine and GL state, isolate UI from the HUD and only suppress vanilla rendering once a complete frame and input path are verified. Cleanup requires the owning current context; on context loss, forget old names rather than deleting them in the replacement context.

## Texture compositing groundwork

`panel_projection.hpp` transforms a world-space panel with a supplied OpenGL view-projection matrix into homogeneous clip coordinates, rejecting near-plane crossings rather than drawing corrupt geometry. `panel_compositor.hpp` is a GLES 3 shader compositor that draws the capture texture as a perspective-correct quad in the currently bound framebuffer. It restores its GL state and refuses invalid clip coordinates. This is a screen overlay without world depth/occlusion, assumes straight-alpha texture data, and requires a texture not attached to the current draw framebuffer. Host tests simulate GL; neither shader compilation nor state restoration has been validated on an Android driver or Bedrock's render-state cache. The code is not hooked into the game: camera matrix acquisition, UI-only capture, correct alpha convention and engine state synchronization still need verification before use.

## Reference investigation

The supplied Drive archive contains `spatial-gui-1.9.1+26.3-fabric.jar`, a Minecraft **Java** Fabric mod, not a Bedrock or LeviLauncher native mod. Its metadata names [tastytrash/Spatial-GUI](https://github.com/tastytrash/Spatial-GUI) as its source and MIT as its license. The archive cannot be loaded directly by this project. The Java implementation was inspected at revision `5e30a418b7cc22634ecd10bed2b49aa73ef88095`: `TextureTargetManager` manages a transparent off-screen target, `ScreenExtractor` captures an isolated GUI render, and the renderer composites that texture into the world. These are useful architectural references, not compatible Bedrock APIs; no code from the Java mod has been copied here.

The supplied launcher is [LiteLDev/LeviLaunchroid](https://github.com/LiteLDev/LeviLaunchroid), inspected at revision `cc5c7bc6eac48f1e82adf705b8b5f63ba0883247`. `MinecraftActivity.dispatchTouchEvent` forwards touch events to `PreloaderInput` and then normally dispatches them to the game. This confirms the Android input route exists, but does not establish a supported way for this native mod to replace game touch coordinates or inject a complete gesture. The BedrockToolsPlus baseline already targets Bedrock `1.26.60.X`; engine behavior still needs device verification.

## Opt-in runtime diagnostics

`Spatial GUI Diagnostics` is a separate, disabled-by-default module for on-device investigation, not a spatial inventory. It hooks the candidate screen-render function when explicitly enabled, forwards each invocation to the original exactly once, and logs up to eight samples while any generic container controller is open. It separately logs up to four hook invocations at enable and resets this budget on each container open, including whether a container and EGL context are present, and logs up to sixteen container open/close events, so missing samples can be distinguished from missing hooks. Android log tag: `BTP-SpatialDiag`. Each sample reports viewport dimensions and whether the draw framebuffer changed during the call. It also logs up to two existing EGL swap-frame events after enabling and after each container opens; their absence can mean the EGL hook is unavailable or the game uses another presentation path. It does not identify which view belongs to the container, capture pixels, change the framebuffer, or intercept touches. The hook is based on a unique binary pattern plus a reference ABI from another platform; it remains unverified on Android and may crash if the match or ABI is wrong. Test only on a disposable world, with backups. Disabling stops observation, though the pass-through hook remains installed for the process lifetime. A missing hook is logged as unavailable. Host tests exercise the pass-through and sample limit using fakes, not a real game or GLES driver.

## Device observation (user recording)

On the user's Android device, the recording shows `container event: open controller_present=1` followed by four `screen hook called: container_open=1 egl_context=0` samples. Thus the container event and candidate screen hook are invoked, but those sampled calls do not have a current EGL context on their calling thread. This does not establish which graphics API the game uses or whether another render thread has an EGL context. In particular, the GLES off-screen capture and compositor must not be called from that screen hook based on the current evidence. The code remains diagnostic and the ordinary container UI remains active.

## Screen identification research

LeviLamina's public `UIRenderEvent.cpp` describes a `ScreenView::render(UIRenderContext&)` hook, and its `ScreenView` headers expose an owning `mController`; Lamium's `ScreenTracker` uses that controller and screen focus to recognize the currently displayed container. These projects target a different API/platform and their field layouts must not be assumed valid on Android 1.26.60. The user-supplied binary has a unique match for the existing `ScreenViewRender` pattern, but that does not prove the matched function is the same method or that its controller field is at any particular offset. The existing Android hook reports controller open and destructor, not focus or actual on-leave; keeping a raw pointer and dereferencing it during a render would risk stale memory.

`container_tracker.hpp` now provides a host-tested, synchronized identity-only tracker for opened and closed controllers. It does not read pointers, identify chests or determine focus, and is not yet connected to an engine hook. A safe integration still requires verifying the 1.26.60 Android `ScreenView` layout, controller association, lifetime, and render-target behavior in the running game.

## User-supplied Bedrock binary check

The user-supplied library is ELF64 AArch64 and contains the version string `1.26.60.04_RC3`. A static scan of its executable sections found one byte-pattern match for each of the nine existing candidate screen, container and renderer signatures listed in `scripts/check_spatial_signatures.py`. Run the checker locally against a legally obtained library; the library itself is not part of this repository. These are pattern matches only, not proof of function identity, ABI, render-target behavior, or support for other 1.26.60 builds. In particular, the candidate screen-render function is not safe to hook solely on this evidence; the association between a screen view and a chest controller, its render timing, and the engine's render target/state ownership remain unverified.

## Integration still needed

- Identify the actual chest screen and lifecycle, including double chests, closing and world transitions. Existing `ScreenStateEvent` reports a generic container controller, not a chest position or type.
- Find a version-verified way to render the live Bedrock container UI to a texture and draw it on the panel. Existing screen-render signatures alone do not establish a safe ABI or render-to-texture path. Preserve the original screen if this is unavailable.
- Map mobile touch and other input back to the original screen's coordinate system, including drag, release, cancellation and screen resizing. Do not synthesize inventory transactions from unverified native function signatures.
- Handle screen focus, occlusion, camera movement and multiple controllers. Restore normal UI/input on every failure or close path.
- Validate on the supported Android Minecraft version and a real device; host geometry tests cannot validate engine hooks, UI rendering, or inventory actions.

Run the geometry test with `./scripts/run_tests.sh` (or compile the test directly as documented at its top).
